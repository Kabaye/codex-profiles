## Routing mechanics

[Official subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) supports standalone roles, model/effort pins and `[agents]` defaults. Named role settings apply after spawn/default resolution. Pin **both** model and effort. The current repository deliberately avoids generated `default` / `worker` / `explorer` aliases and explicitly requests `luna_worker` or `sol_worker` instead.

The [V2 spawn implementation at 0.153.4](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs) shows why named roles and explicit bounded forks matter: full-history unnamed spawns can skip the configured default role. Root inheritance cannot be prevented by a prompt that merely says “use a cheap agent.” This repository forbids omitted/full-history forks and unapproved roles; if a required pin cannot be verified, delegation does not proceed.

The [current configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) documents `agents.enabled`, `max_concurrent_threads_per_session`, `default_subagent_model` and `default_subagent_reasoning_effort`. The cap counts open child threads, excluding the root. The [configuration source](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/config/src/config_toml.rs) identifies `max_depth` as V1-only, ignored by V2. Workers therefore also set `agents.enabled = false` and forbid nested process workarounds; live effective configuration still needs verification.

The old recipes that forced Multi-Agent V2 with scalar feature flags are **not** restored. The empty mode-hint override remains useful, but its scope is now explicit:

```toml
[features.multi_agent_v2]
multi_agent_mode_hint_text = ""
```

`lite` and `strict-common` are fixed team profiles and keep this override. `private` and `work` install in native `solo` by default and therefore install **no** repository mode hint, child cap, custom worker roles, or routing block. Switching either profile to `team` adds the empty hint plus the repository routing policy. This preserves normal Codex explicit-user-requested subagents in solo while reserving proactive selective delegation for team mode.

The setting is a mode-guidance override, not a backend-version override. Current Codex source resolves a configured `multi_agent_mode_hint_text` ahead of catalog/effort mode hints, and the multi-agent-mode tests include an empty-configured-hint case that emits no mode message. The September 2026 regression where an expected proactive work task received explicit-request-only guidance remains useful evidence for why team mode needs the override; it is no longer a reason to override native behavior in solo.

## Memory and context are separate systems

Memory extraction/consolidation have model selectors; these presets do not invent corresponding effort selectors. The [consolidation implementation](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/memories/write/src/phase2.rs) uses the provider-preferred model when no override exists. It is not evidence that the root's model automatically becomes the memory model. private retains provider defaults; other profiles preserve Luna model routing without changing collection/retention policies.

Codex exposes experimental context management through `[features.context_management] experimental_mode = true`; current Codex source/schema also contains this exact key. The user explicitly chose to enable it in **all four profiles**, so every profile now carries that setting. It remains experimental and is separate from Memories: enabling it does not prove universal access to historical sessions, does not change memory retention policy, and should still be verified on the installed client.

## Quality/usage evidence versus our choices

[Artificial Analysis, September 3](https://artificialanalysis.ai/articles/benchmarking-gpt-6-astra), found Astra Max approximately equal to Sol Max in coding cost per task with fewer tokens, while its intelligence evaluation had worse cost efficiency. This counters both “newest is always best” and “expensive token means expensive completed task.” The evaluations do not establish a Codex subscription quota multiplier.

[Shinsuke Kagawa's September 5 firsthand comparison](https://dev.to/shinpr/switching-from-gpt-56-sol-to-gpt-6-astra-start-with-medium-effort-25ao) favors Medium as a starting point and reports different bugs found by different efforts. It is a useful single-project experiment, not independent multi-project consensus. The current `private` policy intentionally chooses **GPT-6 Astra xhigh as the installation root** and has no Astra child role. In `solo`, native Codex behavior is left untouched. In `team`, hard reasoning, integration and acceptance remain in the root; GPT-6 Sol xhigh is the default substantial implementation worker, while GPT-6 Luna Max is reserved for clearly mechanical low-risk work with a settled specification.

The September 22 policy deliberately raises the strong worker lane to GPT-6 Sol xhigh. This is a usage choice for the user's high-quota subscription rather than a universal claim that xhigh is always optimal; representative tasks and actual quota consumption should be monitored.

The current repository caps `lite` at 1 child and fixed-team `strict-common` at 4. `private/team` and `work/team` use a hard cap of **2 open child threads per root session**, with zero or one worker as the normal case. `private/solo` and `work/solo` install no repository-owned child cap.

The [Astra release discussion](https://www.reddit.com/r/codex/comments/1w7j5jf/astra_release_megathread/) contains contradictory firsthand quality and usage experiences. No exact quota ratio or universal effort sweet spot was inferred from engagement or anecdotes.

`work` uses GPT-6 Sol xhigh as the default root and GPT-6 Luna Max as the ordinary delegated path. It also installs GPT-6 Sol xhigh as the strong personal-lane worker. Personal mode is intentionally **not inferred** from the project, repository, selected root model, task content, or difficulty. It activates only after the user explicitly says that the current objective is personal, for example `это личная задача`; a new unrelated objective resets to the ordinary Luna-only lane. Selecting Astra affects only the root and does not activate personal mode.

## Remaining boundaries

This is not a security or spending firewall. Project/plugin roles, config precedence, full-history behavior, explicit unrelated processes and future client changes require local review. The strongest practical team arrangement here is explicit model+effort pins, explicit named roles, bounded forks, disabled child delegation, limited open threads, the empty built-in mode-hint override and fail-closed delegation policy. Solo intentionally removes those repository routing controls and returns multi-agent behavior to Codex.

The original September 6 research environment did not execute a live authenticated Codex task. The earlier GPT-5.6 Luna V2 override was separately smoke-tested by the user before being retired from the current Lite design. Static repository tests still do not prove account entitlement, backend quota behavior, or future-client compatibility. See [verification](verification.md) for the current checks.
