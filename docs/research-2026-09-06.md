## Routing mechanics

[Official subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) supports standalone roles, model/effort pins and `[agents]` defaults. Named role settings apply after spawn/default resolution. Pin **both** model and effort. Aliases named `default`, `worker`, `explorer` override built-ins and reduce accidental inheritance; they are not a comprehensive allowlist.

The [V2 spawn implementation at 0.153.4](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs) shows why named roles and explicit bounded forks matter: full-history unnamed spawns can skip the configured default role. Root inheritance cannot be prevented by a prompt that merely says “use a cheap agent.” This repository forbids omitted/full-history forks and unapproved roles; unsupported behavior falls back to **no delegation**, not a fabricated pin.

The [current configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) documents `agents.enabled`, `max_concurrent_threads_per_session`, `default_subagent_model` and `default_subagent_reasoning_effort`. The cap counts open child threads, excluding the root. The [configuration source](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/config/src/config_toml.rs) identifies `max_depth` as V1-only, ignored by V2. Workers therefore also set `agents.enabled = false` and forbid nested process workarounds; live effective configuration still needs verification.

The old `features.multi_agent_v2` recipes are not copied into new installs. Use the current documented agent controls and the model's real V2 metadata. Do not convert a model to V2 by editing its catalog entry.

## Memory and context are separate systems

Memory extraction/consolidation have model selectors; these presets do not invent corresponding effort selectors. The [consolidation implementation](https://github.com/openai/codex/blob/ac192cd7937b0d73edc6dffe009940ae53782dd4/codex-rs/memories/write/src/phase2.rs) uses a provider-preferred fallback when no override exists. It is not evidence that the root's model automatically becomes the memory model. x20 retains provider defaults; other profiles preserve Luna model routing without changing collection/retention policies.

Astra's new context management can use notes and retrieval of earlier context. The config reference exposes `[features.context_management] experimental_mode = true`. This is a distinct, experimental capability, not proof of universal semantic access to every old Codex session or a reason to enable more personal recording. It is **not enabled by these presets**. Evaluate separately on a bounded long-context task before changing a working setup.

## Quality/usage evidence versus our choices

[Artificial Analysis, September 3](https://artificialanalysis.ai/articles/benchmarking-gpt-6-astra), found Astra Max approximately equal to Sol Max in coding cost per task with fewer tokens, while its intelligence evaluation had worse cost efficiency. This counters both “newest is always best” and “expensive token means expensive completed task.” The evaluations do not establish a Codex subscription quota multiplier.

[Shinsuke Kagawa's September 5 firsthand comparison](https://dev.to/shinpr/switching-from-gpt-56-sol-to-gpt-6-astra-start-with-medium-effort-25ao) favors Medium as a starting point, yet retains a High implementation and reports different bugs found by different reviewers. It is a useful single-project experiment, not independent multi-project consensus. Our Medium root / Sol High execution / Astra High specialist policy is **a testable design choice**, not a quoted official recommendation.

The [Astra release discussion](https://www.reddit.com/r/codex/comments/1w7j5jf/astra_release_megathread/) contains contradictory firsthand quality and usage experiences. No exact quota ratio, universal sweet spot or guaranteed verifier benefit was inferred from engagement or anecdotes.

`x20-work` deliberately keeps Luna Max as the ordinary-work default but also installs a pinned Sol High role. This is a product-policy choice for a mixed-use machine: clearly personal objectives can use the same stronger delegated execution model as x20 without making normal work automatically more expensive. Root selection and task classification remain independent; selecting Astra does not itself enable or require Sol children. No separate authorization marker is used.

## Remaining boundaries

This is not a security or spending firewall. Project/plugin roles, config precedence, full-history behavior, explicit unrelated processes and future client changes require local review. A universal Luna-only child guarantee with an unrestricted root catalog was not established. The strongest practical arrangement here is native model+effort pins, pinned compatibility roles, current defaults, bounded forks, disabled child delegation, limited open threads and fail-closed delegation policy.

No live authenticated Codex task, backend effort acceptance, multi-agent smoke test, Windows execution or local history/Skills inspection was performed in the research environment. See [verification](verification.md) for the actual static test scope and the remaining checks.
